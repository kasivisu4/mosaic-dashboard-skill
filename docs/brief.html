Mosaic Dashboard Planner
Project brief · Kasi Vandanapu · October 2026

A planner that decides, an executor that builds

Dashboards built with Claude took about 40 minutes and their charts didn't filter each other. This project splits the work. A planner skill reads who the dashboard is for, understands the data with DuckDB, agrees the story with the person, and writes a plan. An executor turns the plan into a cross-filtered dashboard. For v1 the executor is Claude's own building capabilities; it can be swapped later without touching the planner.

03 · How involved

Three creation modes

Each persona has a default; the person can override with “just build it” (Quick) or “show me the queries” (Deep). With no signal, Guided.

LEVEL 1 · QUICK

Build straight through

“Just give me a dashboard of this.”

  • No questions; assumptions listed at the top
  • Plan and build note still produced
  • Ends with 2–3 suggested refinements

Default for executives and first looks.

LEVEL 2 · GUIDED

Confirm, then build

“Help me build a dashboard for the team.”

  • Data check after profiling
  • Story check before the plan goes to the executor
  • Refine loop after delivery

Default for storytellers and when unclear.

LEVEL 3 · DEEP

Work through it together

“I want to see how each number is calculated.”

  • Guided, plus the full profile shown
  • DuckDB SQL per metric approved before building
  • Exploration, SQL and caveats on the page

Default for analysts and researchers.

04 · One request, end to end

Planner, handoff, executor

Example: card_transactions.csv with “Make me a dashboard of Q3 spend, I want to see where fraud is happening.” Steps marked ask are checkpoints.

    05 · The handoff

    The plan is plain Markdown, not a spec

    No schema and no renderer. The planner writes a short, readable plan; any executor (Claude now, something else later) can follow it, and the person can read and edit it at the story check.

    ## Dashboard plan
Persona: executive   Mode: Guided
Destination: claude.ai artifact

### Data
card_transactions.csv · 1 row = 1 transaction · 2.1M rows
Excluded: 3 negative amounts (refunds)
Fraud rate = flagged txns / all txns  (confirmed)

### Story
1. KPIs: spend · fraud rate · flagged spend
2. "Fraud rate doubled after Aug 20"       trend, brush
3. "Online electronics leads flagged spend" ranked bar, click
   (swapped in for region at story check)

### Interaction
Every chart and KPI filters on: week brush, mcc click
Reset button. No SQL shown (executive).

### Data for the executor
weekly_mcc.parquet  -- DuckDB aggregate, 1,092 rows
SQL: SELECT date_trunc('week', txn_date) AS week, …

    What each section is for

    • Persona, mode, destination tell the executor what to show and which stack to use.
    • Data records what the person confirmed, so the executor never re-decides a definition.
    • Story is the outline approved at the story check, with titles written as findings.
    • Interaction states the cross-filtering rules in words.
    • Data for the executor is the DuckDB output plus the SQL that made it, so every number traces back.

    The same plan text goes into the build note on the finished page.

    07 · Feedback and quality

    How it gets better

    Inside one conversation

    Profile→Data check→Story check→Build→Refine↺

    The person corrects course before anything is built. Every answer lands in the plan and the build note.

    Across conversations

    Refine answers→Same fix twice?→New planner rule→Eval rerun

    Repeated corrections become rules. Build notes show which step a weak dashboard skipped.

    ## Asking rules  (planner SKILL.md)
- Ask only when the answer changes the plan.
- Max 3 questions per checkpoint, one batch,
  multiple choice from the profile; mark the

  state the assumption.

    Project instructions

    Standing context for every chat in the project.

    Project: Mosaic Dashboard Planner

Goal: a reusable way for people using Claude to get good, cross-filtered dashboards quickly. Split into a PLANNER (a Claude skill) and an EXECUTOR (v1: Claude's own building capabilities).

Decisions already made:
- The planner holds only decisions: persona, mode, checkpoints, data understanding, story, interaction rules, styling rules. No semantic layer, no JSON spec, no custom renderer.
- DuckDB is required. Use Python DuckDB in the code sandbox for profiling, checks, aggregation and the SQL behind every metric.
- Personas: executive, data analyst, storyteller, researcher. The planner infers the persona from the request and asks one intake question only when signals are weak.
- Modes: Quick (no questions, assumptions listed), Guided (data check + story check + refine), Deep (Guided + full profile + SQL review + exploration). Each persona has a default; the person can override.
- Asking rules: ask only when the answer changes the plan; max 3 multiple-choice questions per checkpoint built from the profile, with a recommended option; skip when already answered; use recommended options when nobody answers; never ask about chart library or styling.
- Handoff: the planner writes a plain Markdown plan (persona, mode, destination, confirmed data definitions, story with finding-titles, interaction rules, data files + SQL). The executor follows it; the plan is copied into a build note on the page.
- Executor stacks: local HTML -> Mosaic + DuckDB-WASM. claude.ai artifact -> d3 or Vega-Lite over pre-aggregated data (DuckDB-WASM is blocked there by default; the engine is 35.7 MB vs a 15 MB per-file limit). The built-in Dashboard artifact type is an optional executor (d3 only, data files up to 8 MB).
- Skill packaging for claude.ai: folder named after the skill containing Skill.md, zipped, uploaded in Settings > Capabilities > Skills.

Working style: short, direct answers. Prefer building and testing over long plans. Keep each skill file focused; keep Skill.md short and point to references.

    First-session prompt

    Paste into the first chat in the project.

    Let's start building the dashboard planner skill described in the project instructions.

Step 1 only for this session:
1. Write dashboard-planner/Skill.md with the trigger description, the workflow (read intent -> understand data -> data check -> story -> story check -> write plan -> hand to executor -> review -> refine), the mode table, the asking rules and the plan template.
2. Write references/understand-data.md: the DuckDB profiling recipe (SUMMARIZE, grain, column classes, date coverage, outliers, 3-5 written observations).
3. Write scripts/profile.py: profiles any CSV or Parquet with Python DuckDB and prints a compact summary.
4. Generate a small sample card-transactions CSV (txn_date, region, mcc_group, amount, fraud_flag), run profile.py on it, and show me the output.

Then stop and tell me what you'd change before we do personas and the executor.
